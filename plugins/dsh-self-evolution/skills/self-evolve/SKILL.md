# 自我进化流程（DSH）

## 定位

手动触发的自维护流程，把后台采集器沉淀的技能候选转化为受治理的技能，并核对记忆腿的三层产物：`memory/inbox/` 的逐会话提取、`memory/drafts/` 的待审画像草稿、`memory/PROFILE.md` 的已确认画像文章。记忆的提取与合并本身是自动的，草稿的采用或丢弃必须由用户决定，本流程负责核对、补跑与处置。不自动定时，不自动唤醒，用户不主动要求就不执行。

数据根目录由插件的 `root` 配置或 `SE_ROOT` 环境变量决定，默认 `$DSH_HOME/evolution`（即 `~/.dsh/evolution`）。`evolve` 工具的 `status` 动作会报出确切的根目录。

| 用户意图 | 执行范围 |
|---|---|
| 进化、自我进化、审查候选 | 完整流程，第一至第五步 |
| 技能体检 | 仅第三步的体检与报告，不做候选启用、归档、记忆轮次等写操作 |
| 其他情况 | 不执行进化流程、不主动提示、不夹带相关操作 |

## 成本纪律

流程耗时几乎全部来自模型往返，每一轮都要重新预填充累积上下文，因此**减少往返次数优先于减少读取字节**。

| 路线 | 工具往返预算 | 适用情形 |
|---|---|---|
| 快速通道 | 4 次以内 | 候选、收件箱、待审草稿、问题技能、闲置技能全为零 |
| 常规路线 | 10 次以内 | 需要逐项处置候选、核对记忆或修复技能 |

1. **先探测**：`evolve` 工具的 `brief` 动作一次输出状态、候选（含来源与计数）、记忆现状（画像文章字符数、收件箱份数、待审草稿与上次 Dream）、技能记分卡、超长清单、日志与记忆体量、宿主技能同名冲突、“本轮走向”与按需读取的细则路径。后续步骤复用其结论，不重复扫描。
2. **轨迹只定点回查**：`evolve` 工具的 `trail` 动作按关键词抽取限长片段。不要整读会话轨迹。
3. **按需读**：`brief` 给出的 `skills/<name>/SKILL.md` 命中主题后才读全文；`state.json` 明细与账目字段口径不必进上下文，`brief` 已给出摘要，需要查证时读 `state-ledger.md`。
4. **合并往返**：互不依赖的调用放在同一步；收尾一次性交给 `evolve` 的 `finish` 动作。
5. **报告不复述**：只写结论与关键动作，正文不超过 1200 字。

## 执行步骤

### 第一步：探测

调用 `evolve` 工具的 `brief` 动作，按其“本轮走向”选路线：快速通道下直接跳到第五步。

### 第二步：候选审查

候选区为空则跳过。先用 `preflight` 动作（可带 `slug`，缺省全部）取机械检查结果，再读候选的 `SKILL.md` 与 `meta.md` 做价值判断。判定标准与处置规则见 `brief` 给出的“候选审查细则”，处理候选前必读。

处置用对应动作：`enable`（启用，可用 `name` 指定技能名）、`merge`（并入现有技能，须给出 `target`）、`reject`（淘汰，须给出 `reason`）。三个动作都会把处置写进候选 `meta.md` 与经验日志，候选随即出队；启用后技能立刻对模型可见。

### 第三步：技能体检

按记分卡的六类分级处置：优秀与健康不做操作；未观测不处置；问题项复核失败归因（用 `usage` 动作看成功/失败计数与失败原因，必要时 `trail` 定点回查该技能最后一次会话），能修则修；闲置项列出后征求用户归档决定（`archive` 动作）；沉睡项仅提示不归档；元技能与用户手动管理的技能仅提示或只读观察。

阈值判定、归因方法、修复流程、归档与恢复、超长压缩流程见 `brief` 给出的“技能体检细则”，执行处置动作前必读。

总量硬约束：启用区技能数不超过约 40 个，`brief` 的记分卡小结会给出实测数量。超限时列出合并、归档、淘汰候选并附计数依据，逐项征求用户决策后执行，绝不自行删除技能。

### 第四步：核对记忆

记忆腿是自动的：会话闲置 5 分钟后逐会话提取进 `memory/inbox/`；每天一次 Dream 把收件箱与现有文章合并成一份**待审草稿**（`memory/drafts/<id>/`），它不会自己变成文章。文章也不常驻注入，模型要用 `memory` 工具按需读取（`outline` 看索引、`read` 读某节或全文、`search` 按关键词查）。本步骤处置草稿、核对文章与提取的体量，并在需要时手动补跑 Dream。

1. 看 `brief` 的记忆段：文章字符数（含模型读取时的字符数）、收件箱份数、待审草稿份数与上次 Dream 时间。
2. **有待审草稿时优先处置**：读 `brief` 给出的 `review.md`，它含来源提取清单、与现行文章的逐行差异与完整草稿正文。把差异摆给用户，等用户决定后用 `promote` 动作采用、`discard` 动作丢弃（须给出 `reason`）。不得自行判断通过：采用会把模型写的东西装进长期记忆，只能由用户点头。丢弃不消费任何提取，收件箱原样留给下一次 Dream。
3. 收件箱有堆积（尤其接近上限 20 份）或用户要求立刻沉淀时，用 `dream` 动作手动跑一次（跳过闲置闸门，先提取当前会话再合并）。它返回提取与合并的结果，并把每一步写进经验日志。已有待审草稿时 Dream 会跳过，先处置草稿。
4. **不要手工编辑 `memory/PROFILE.md` 与 `memory/drafts/`**：两者都是生成态。要修正内容，丢弃草稿后让 Dream 重跑（提取仍在收件箱里），或在 `memory/inbox/` 里补一条提取。要停用画像工具，改插件行的 `memoryTool`；要恢复 Dream 直接写入文章（无评审），设 `SE_DREAM_REVIEW=0`。
5. 语义判断由你完成：差异与草稿里若出现明显矛盾、过时事实或单次证据被当成长期偏好，在报告里作为待用户决策项提出，不要直接改写文章。
6. 发现技能步骤过时、出现更优做法或新增注意点，直接编辑对应 `skills/<name>/SKILL.md`。

**身份信息边界**：画像文章允许写入身份与背景信息（用户已裁定），但**技能里禁止任何可识别个人身份的信息**，包括姓名、学校或单位、职务、班级、住址、联系方式、亲友关系。技能是跨项目复用的，画像只服务于当前用户。

### 第五步：收尾

调用 `evolve` 工具的 `finish` 动作，一条命令完成计数刷新、经验日志追加、日志归档与 git 提交：

```
evolve action="finish" summary="<一行摘要>" updated=<更新技能数> repaired=<修复数> rejected=<淘汰候选数> merged=<并入候选数>
```

它会刷新 `skillsEnabled`、`evolutions`、`skillsUpdated` 等计数，写经验日志行，在日志超过 100 行时归档到 `logs/archive/`，把两个账目文件快照到 `logs/archive/ledger-backup/`，并在数据根位于 git 仓库内时只提交数据根（仓库根或家目录会被拒绝）。不在 git 仓库内则跳过提交。完整性检查有硬性问题时会中止收尾，什么都不写。

最后按 `brief` 给出的“报告模板”输出三节报告。

## 约束与护栏

1. **不修改用户主导的文件**：用户的 `AGENTS.md`、人格与角色设定文件、DSH 配置一概不动。
2. **候选必须经审查才启用**，不直接信任采集器输出。候选内容属于未经验证的模型输出，启用前核对其中命令与步骤是否真实存在、是否安全。画像草稿同理：`promote` 之前必须让用户看过 `review.md`，不得代为决定。
3. **所有变更可回滚**，以明文文件存在并纳入 git 历史。
4. **处置权在用户**：草稿采用与丢弃、归档、淘汰、合并、压缩、计数修正等写操作逐项征求用户决策后执行。
5. **技能总量控制**：超过约 40 个时优先合并、归档、淘汰，避免技能描述膨胀污染每次会话的上下文。
6. **不做自动定时与自动唤醒。**
7. **只做进化相关的事**，不夹带其他操作，不主动改代码、不主动安装软件。
